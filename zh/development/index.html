开发#

本节面向贡献者。本页介绍如何准备本地仓库，以及检查项和拉取请求的规则。 编写文档 介绍文档的组织、写法和翻译， 发布到 PyPI 介绍如何发布版本。

环境准备#

克隆仓库，以可编辑模式安装，并同时安装测试、文档和代码检查依赖，然后安装 pre-commit 钩子。

git clone https://github.com/gchensy/kivi.git
cd kivi
python -m pip install -e '.[test,docs,lint]'
pre-commit install

构建与验证#

ruff check .
ruff format --check .
python -m pytest
python -m sphinx -W -b doctest docs docs/_build/doctest
python docs/build.py

ruff 按 pyproject.toml 中的规则检查代码并统一格式。pre-commit 钩子会在每次提交前运行它， build 检查也会在每个 pull request 上运行它。另一个任务会用 kivi 支持的最低版本 NumPy 和 pandas 运行测试。

doctest 构建器会运行本文档页面和 docstring 中的全部示例。HTML 构建会在 docs/_build/html 下生成英文和简体中文两套文档。API 签名从已安装的包提取。

拉取请求#

从最新的 master 创建分支，每个拉取请求只做一件事。master 分支只接受通过拉取请求合入的改动，而且分支必须已与 master 同步，并通过 Documentation 工作流的 build 检查。因此，每个拉取请求都会和此前已合并的全部改动一起测试。要更新分支，把 master 合并进来即可。合并后的分支会被自动删除。

修改相同文件的拉取请求应依次完成和合并，不要并行开发。有两类文件几乎每个拉取请求都会改动，它们的组织方式让冲突很少发生：

  • 发布说明。在新文件 docs/release/unreleased/<topic>.<category>.rst 中，把每项面向用户的改动写成一个列表项，其中类别为 new 、 changed 、 fixed 或 removed 。不要直接编辑 版本说明 ：这些文件会显示在其中的“未发布”标题下。

  • 翻译目录。合并或变基因 kivi.po 冲突而中止时，运行 python docs/build.py --merge-po 。它会保留双方的翻译，并加入合并后新出现的文本。翻译这些文本后，再把目录加入提交。

因此，新增模块的拉取请求只需新增文件：模块本身、它的测试、一个用户指南页面、 docs/api/ 中的一个 API 页面，以及一条发布说明。API 参考和用户指南会自动收录新页面。描述整个库的页面会在一批这样的拉取请求合并之后统一更新，见 编写文档 。
