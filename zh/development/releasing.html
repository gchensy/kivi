发布到 PyPI#

推送版本标签时，Release 工作流会把 kivi 发布到 PyPI。它使用 PyPI 可信发布（trusted publishing），因此仓库中不保存任何 API 令牌。

  1. 把 pyproject.toml 中的 version 改为新版本号，例如 0.3.1 。运行 python docs/build.py --release 0.3.1 ，它会把发布说明文件移入 版本说明 中以当天日期命名的新章节；然后翻译新章节的标题。

    如果 python docs/build.py 仍报告有入口页面需要更新，这条命令不会做任何改动，详见 编写文档 。

  2. 将改动合并到 master 分支。

  3. 在合并后的提交上打 v 加版本号的标签，并推送该标签：

    git switch master
git pull
git tag v0.3.1
git push origin v0.3.1

推送标签后上传会直接开始，没有审批环节，因此只在准备好发布时才推送标签。如果标签与版本号不一致，或者标签指向的提交不在 master 上，工作流会在上传任何内容之前停止。否则它会运行测试，构建源码包和 wheel，用 twine 检查后上传到 PyPI。上传成功后，它才会创建 GitHub release，附上安装包，并根据已合并的拉取请求生成说明。0.4.0rc1 这类版本会被标记为预发布。

仓库在三处保护这条发布路径：

  • 只有仓库管理员可以创建、移动或删除 v* 标签。

  • pypi 环境只接受来自 v* 标签的部署。

  • PyPI 只信任 gchensy/kivi 中在 pypi 环境下运行的 release.yml 工作流。

PyPI 不接受重复上传同一个版本。如果运行在上传之前失败，可以用 git push origin :refs/tags/v0.3.1 删除标签，修复问题后重新打标签。如果已经上传成功，请用新的版本号发布修复。

版本号#

每个版本都遵守 兼容性 中的承诺。从 1.0 起：

  • 只修复错误的版本是补丁版本，例如 1.3.1。

  • 扩充 API、弃用其中一部分或提高最低版本的版本是次版本，例如 1.4。

  • 移除或修改先前版本所弃用内容的版本是主版本，例如 2.0。

对错误结果的修复可以进入补丁版本或次版本，并附上说明错误所在的 fixed 片段。

弃用#

已弃用的名称、参数或行为继续可用，并通过 _deprecation.warn 发出 FutureWarning ；无论检查位于多深的调用层级，该函数都会把警告指向调用者所在的行。消息指出被弃用的内容，并说明替代用法。 tests/test_deprecations.py 用 pytest.warns(FutureWarning, match=...) 检查每个警告，并检查它指向测试自身所在的行。代码、文档和 README 示例本身不得触发弃用警告，因为测试和 doctest 会把警告变为错误。

该版本的 changed 片段指出所弃用的内容及其替代用法。移除它的主版本在 removed 片段中列出这次移除，并删除相应的测试。

最低版本#

Python、NumPy 或 pandas 的最低版本只在次版本中提高，并由前一个版本的 changed 片段预先公布。提高最低版本的那个版本要同时修改 pyproject.toml 中的 requires-python 或 dependencies 、 .github/workflows/docs.yml 中测试最低支持版本的 minimum-versions 任务，以及 安装 和 兼容性 上列出的版本。
