# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It holds the rules and a map of the code. What a function computes, its tie and tolerance rules and its references are in its docstring, its tests and, where its release has one, the design document of that release (`docs/design/`). Read those before changing a function.

## Commands

```bash
python -m pip install -e '.[test,docs,lint]'   # required first: docs/conf.py reads installed package metadata
pre-commit install                          # once per clone: run ruff and mypy on every commit
ruff check . && ruff format --check .       # what CI's build job runs before the tests
mypy                                        # type-checks src/kivi with the [tool.mypy] settings in pyproject.toml; CI's Lint step runs it after ruff
python -m pytest                            # unit tests
python -m pytest --cov                      # unit tests with branch coverage, as CI runs them; fails below fail_under in pyproject.toml
python -m pytest tests/test_core.py::test_woe_matches_hand_calculation   # single test
python -m sphinx -W -b doctest docs docs/_build/doctest   # runs every >>> example in docs/**/*.rst and in docstrings (pytest does not collect them)
python docs/build.py                        # checks the zh_CN catalog and the API pages, lists entry-point gaps, then builds en + zh HTML into docs/_build/html with -W
python docs/build.py --update-po            # after editing English text: merge new/changed strings into kivi.po
python docs/build.py --merge-po             # after a merge/rebase stops on kivi.po: keep both sides' translations, then update
python docs/build.py --release 0.4.0        # at release time: move docs/release/unreleased/* into a section dated today; refuses while entry-point gaps remain
```

## Tooling

- **ruff** lints and formats every Python file (`[tool.ruff]`: line length 100, target py311, rules E/F/W/I/B/UP/NPY/D with the numpy docstring convention; tests and docs scripts are exempt from D). Markdown is excluded because the README code blocks align their comments by hand. The ruff version is pinned in the `lint` extra and as `rev` in `.pre-commit-config.yaml`; bump both together.
- **mypy** and pandas-stubs are pinned only in the `lint` extra. The pre-commit mypy hook is `local` (`language: system`), so there is no second version to keep in sync, and NumPy's stubs come from the installed NumPy. Bump pandas-stubs together with the pandas major or minor version CI installs. `[tool.mypy]` checks `src/kivi` only, with `python_version = "3.12"` (CI's Python) and `warn_unreachable`; tests are not type-checked.
- **Coverage:** `[tool.coverage]` measures branch coverage of `kivi` with `fail_under = 99`; lower it only on purpose.
- **Warnings are errors.** pytest runs with `filterwarnings = error`, so assert expected warnings with `pytest.warns`. `conf.py` also turns warnings raised from doctest code or from `docs/_plotting.py`, `docs/_diagrams.py` and `docs/_tutorial.py` into errors, so an example that demonstrates a warning must catch it with `warnings.catch_warnings(record=True)`. `numpydoc_validation_checks = {"all"}` turns any missing docstring section (including See Also) into a `-W` build failure.
- **Worktrees:** an editable install resolves to the checkout it was installed from; in a git worktree, prefix commands with `PYTHONPATH=src` (or reinstall) so they exercise the worktree's code.
- **Extras:** the runtime dependencies are NumPy and pandas. `test` installs scikit-learn, SciPy and statsmodels next to pytest, because `tests/test_reference.py` compares kivi with them. `plot` (matplotlib >= 3.7) is the optional extra of `kivi.plotting`.

## Architecture

`src/kivi` (src layout, hatchling) is the 0.3 rebuild of the legacy 0.2.x library as a NumPy/pandas core. There are no top-level re-exports: the public API is imported from submodules, and each public module has its own page in `docs/api/<module>.rst` listing every entry point.

### Layers

- **Private helpers** that several public modules need:
  - `_validation`: input checks and conversions (`as_series`, `like_input`, `as_real`, `as_weights`, `shared_index`, `known_outcomes`, `finite_scores`, `binary_labels`, `scores_and_labels` (the score and label checks of every metric), `as_flags` (rule columns), `woe_values` (the tables `woe_trend` takes), `check_class_weights`, `check_count`, `check_smoothing`, `as_generator`, `as_numbers`, `object_index`, `is_missing`, `shown`, `shown_argument`, the column helpers);
  - `_counts`: counting and smoothing (below), `ratio`, `group_rows`, and `concat_groups`, which joins two samples' groups for PSI without hashing an interval `CategoricalDtype` (that warns on NumPy < 2.2) and matches unordered categories by label;
  - `_special`: `special_values`, `special_positions`;
  - `_edges`: `fit_edges`, `band_edges`, `observed`, `weighted_quantile`;
  - `_stats`: the distribution functions (`betainc`, `gammaincc`, `chi2_sf`, `normal_cdf`, `normal_quantile`, `student_t_sf`, `beta_quantile`, `bivariate_normal_cdf`);
  - `_logit`: the IRLS logistic fit (also behind `platt_fit` and `fractional_regression`) and the design-matrix checks that `selection` and `lgd` share;
  - `_deprecation`: `warn`.
- **A public module imports no private helper of another public module.** Public modules may import each other (today `monitoring` and `selection` import `metrics`, `rules` imports `binning`, `spec` imports `binning` and `woe`, `univariate` imports `binning`, `metrics` and `woe`); there are no cycles.
- **Every module imports modules rather than names** (`_validation.as_series`, `typing.Literal`, `numbers.Real`, `abc.Mapping` from `from collections import abc`), so a public module binds only its `__all__`, private names and modules; `tests/test_namespaces.py` checks this.

### Fit once, apply everywhere

Fitting and applying are separate steps. A function fits on the reference (development) sample and returns plain values or a table; another applies them to every sample.

1. **Edges:** `kivi.binning.bin_edges(values, bins, *, method, special)` and the supervised `chimerge_edges`, `tree_edges`, `ks_edges`, `monotonic_edges`, `optimal_edges` (target) and `variance_edges` (continuous response) fit edges on the reference sample only. Interior duplicate edges are collapsed and the endpoints are always `-inf`/`+inf`, so future out-of-range values still land in a bin (a constant reference yields one bin).
2. **Grouping:** `kivi.binning.cut(series, edges, special=...)` applies the same edges to every sample (or `pd.cut` when there are no special values). `special` codes (e.g. bank `pdays == -1`) are left out of the fit and get their own categories ahead of the intervals; without `special`, `cut` returns exactly `pd.cut`'s result. Codes match by equality, also after `pd.to_numeric` for non-numbers (a text `"-1"` gets the code `-1`); boolean codes raise because `True == 1`. Categorical variables are passed as they are, or grouped first with `category_groups` or `chimerge_groups` (a plain dict category → group) and `group_categories(values, groups, *, unseen="raise")`.
3. **Tables:** `kivi.woe.woe_table(groups, target)` and `kivi.stability.psi_table(reference, current)` take grouped series and return one row per group; totals are the caller's `.sum()` of the `iv` / `psi` column.
4. **Encoding:** `kivi.woe.woe_transform(groups, table, unseen="raise")` maps groups back to the fitted WOE and gives missing values the missing group's WOE. A label absent from the table raises unless `unseen` is a number, so new categories never turn into silent NaN.

The same pattern runs through the rest: `fit_spec` → `BinningSpec`, `platt_fit` / `isotonic_fit` → `platt_predict` / `isotonic_predict`, `central_tendency_shift` and `quasi_moment_fit` → a shift or a curve, `master_scale` → `assign_grades`, `score_scaling` / `points_table` → `woe_to_points`. Only `BinningSpec` and `FeatureSpec` are saved as versioned JSON.

### Modules

Each entry says what the module covers and the rules that reach beyond it.

- **`binning`:**
  - ChiMerge, monotonic, optimal and variance binning start from `initial_bins` quantile bins (`_fine_positions`, `_fine_bins`). `optimal_edges` and `variance_edges` share one dynamic program (`_best_binning`) and sum ranges of fine bins with `_range_sums` (aligned power-of-two blocks), so large weights cannot round away small ones.
  - `bin_edges` delegates to `_edges.fit_edges(..., advice=, stacklevel=)`. `gains_table` (via `_edges.band_edges`), `cutoff_table` and `confusion_table` (both through `strategy._cutoff_values`) call it directly, so the tied-quantile warning points at their caller and gives advice that fits it.
  - `tests/test_supervised_binning.py` checks `optimal_edges` and `variance_edges` against exhaustive searches and hard-codes values of optbinning 1.1.0, which is no test dependency because its ortools dependency needs NumPy ≥ 2.0.2.
- **`woe`:** `woe_table`, `woe_transform`, `woe_trend` (its six labels are a public `typing.Literal`) and the count functions `woe` and `iv`.
- **`stability`:** `psi_table`, `psi`, and `csi_table(reference, current, points, *, unseen_points=None)`, whose sum over all variables is the change of the mean score.
- **`features`** (1.3): point-in-time `window_features` and `panel_features`, and `FeatureSpec`. Time columns must have a datetime64 dtype; windows end before the observation time by default. `FeatureSpec` format version 1 is final with 1.3.0; `tests/data/feature_spec_1.3.0.json` and `.features.json` were written by running `tests/test_features.py` as a script and must not change.
- **`selection`:** `correlation_filter`, `vif`, `vif_filter`, `logistic_regression`, `stepwise`, `selection_path` and `SeparationError`. Separation is reported only with a certificate. Weights are frequency weights with statsmodels `GLM(freq_weights=)` semantics. `stepwise(positive=True)` keeps every coefficient positive, as WOE inputs require.
- **`scorecard`:** `score_scaling` (odds as good:bad), `pd_to_score` / `score_to_pd` (exact inverses), `points_table`, `woe_to_points` and `reason_codes`.
- **`expert`:** AHP weights and consistency of pairwise comparison matrices, and `combine_weights`.
- **`metrics`:** `roc_auc`, `gini`, `ks`, `gains_table`, `brier_score`, `roc_table`, `roc_auc_interval`, `delong_test`, `generalized_auc` and `expected_maximum_profit`. They expect a score that rises with the event probability, so pass a PD or `-points`. `tests/test_metrics.py` hard-codes values of empulse, which is no test dependency because it needs NumPy ≥ 1.25.2.
- **`calibration`:** prior correction (`prior_correction`, `corrected_intercept`), `calibration_table`, `herfindahl_index`, the calibration tests (binomial, Jeffreys, Hosmer–Lemeshow, Spiegelhalter), the ECB validation tests (`brier_decomposition`, `concentration_test`, `backtest_table`), Platt and isotonic calibration, the central tendency (`central_tendency_shift`, `quasi_moment_fit`; `docs/design/kivi-1.8-default-rates.md`) and the master scale (`master_scale`, `fit_grade_pd`, `assign_grades`).
- **`strategy`:** scores rise with risk, and a cut-off approves scores at or below it (ties approved): `cutoff_table`, `confusion_table`, `swap_set`, `expected_loss`, `expected_loss_table`. Booleans count as 0 and 1 in `probability`, as in `metrics` and `calibration`, but not in `lgd`, `ead`, `loss`, `revenue` or `weights`.
- **`rules`** (1.7, 1.8): `rule_table`, `rule_set_table` (a decision waterfall) and `rule_candidates` (single-threshold rules fitted with the public `tree_edges` or `ks_edges`). A missing value in a rule raises; a missing target is an unknown outcome. `rule_candidates` computes the counts per candidate, without an n × m boolean frame.
- **`reject_inference`:** `fuzzy_augmentation`, `parceling` and `reweighting`; the weights make the standard errors of a refit too small, and the docs say so.
- **`spec`:** `fit_spec` and the frozen `BinningSpec`. JSON format version 1, or 2 when a column is grouped; `BinningSpec.FORMAT_VERSION` is the newest version it reads, and a newer one is rejected. `tests/data/binning_spec_0.6.0.json` (format 1) and `binning_spec_0.8.0.json` (format 2) were written by the code of those tags (the docstring of `tests/test_spec_compat.py` has the commands). Loading those files and encoding with them are checked exactly: they back the promise that later releases read old files, so a change that breaks them needs a new format version. A fresh fit is compared with them to a relative 1e-12 only, because CPUs with and without AVX-512 round logarithms differently; a deliberate fix of fitted results may update that comparison without a new format version.
- **`univariate`:** `profile_table`, which shares the column helpers in `_validation` with `spec`; its IV is that of a quick `bin_edges` + `cut` + `woe_table` binning.
- **`vintage`:** `delinquency_panel`, `vintage_table` (months a cohort has not reached are NaN, never 0), `transition_matrix`, `roll_rates` (requires `states` unless both inputs are ordered categoricals), `migration_bandwidth`, `migration_test` and `default_rate_table`.
- **`monitoring`:** `monitoring_table` and `stability_table`. Exactly one reference argument is required; the empty categories of a categorical period keep their row.
- **`lgd`** (1.6): `workout_lgd`, `conversion_factor`, `lgd_table` and `fractional_regression`; `docs/design/kivi-1.6-lgd-ead.md`.
- **`capital`** (1.5): the IRB risk-weight functions of Basel CRE31 and China's 2023 rules, the one-factor model (`conditional_pd`, `systematic_factor`, `vasicek_fit`) and `most_prudent_pd`; `docs/design/kivi-1.5-capital-survival.md`.
- **`lifetime`:** `convert_pd`, `transition_pd`, `survival_table`, `expected_credit_loss`, `significant_increase`, `assign_stages` and `stage_table`. The staging functions reject missing values.
- **`plotting`:** charts of kivi's tables (`roc_chart` and `precision_recall_chart` both draw a `roc_table`, `distribution_chart` any table with `non_event` and `event`) and of a correlation matrix (`correlation_chart`).
  - Each takes its table or matrix first and a keyword-only `ax`, draws on a new figure without `ax`, and returns the Axes. `woe_chart`, the one chart with two y-axes, returns the pair (bars, line), as the user decided.
  - The columns are checked before a figure is created. No function calls `show`, changes `rcParams` or mutates its input, and chart text is only column names, argument names and values.
  - matplotlib is imported inside the functions, so `import kivi.plotting` loads no matplotlib; `tests/test_plotting.py` checks that in a subprocess and is skipped without matplotlib.
  - `monitoring_chart` draws bars or a line only by `kind`, never by the column name.
  - `docs/api/compatibility.rst` promises the data drawn, the arguments, the errors and the returned Axes, but not colors, sizes or the placement of legends and annotations.
- **`datasets`:** `load_bank()` loads the bundled `bank.csv` (UCI Bank Marketing, CC BY 4.0, see `DATA-LICENSE.txt`) through `importlib.resources`; tests pin its shape (4521×17) and class counts. `make_loan_panel`, `make_applications`, `make_defaults`, `make_recoveries` and `make_transactions` simulate data from a local generator. The default output of `make_loan_panel` is bit-identical to 1.4.0 (SHA-256 digests in `tests/test_datasets.py`), and new options must keep the default output of every generator. Only `make_loan_panel` has digests; the default output of `make_applications` is guarded only by the doctests and the tutorial that print it.

## Conventions

- **Argument order and names:** the data argument comes first and the target second, as in `woe_table(groups, target)`, `roc_auc(score, target)` and `stepwise(X, target)`. A predicted probability argument is always called `probability`.
- **Inputs and outputs:** public functions accept one-dimensional array_like input through `_validation.as_series`, which leaves Series untouched, and return results shaped like the input (Series, float or array) through `_validation.like_input`. Inputs that describe the same observations (data, target, probability, weights) must have identical indices when two of them are Series, checked with `_validation.shared_index` and `as_weights(..., others=)`; arrays and lists match by position.
- **No mutation, local randomness:** functions must not mutate caller inputs; anything random takes a local seed (`_validation.as_generator`) instead of touching NumPy's global state.
- **Smoothing:** `_validation.check_smoothing(smoothing)` requires a real, finite, positive scalar that is not a boolean; every public function and class with a `smoothing` argument goes through it, and `tests/test_validation.py` checks that the list is complete.
- **Errors:** messages name the argument and show the value received through `_validation.shown` (a Series or Index stands for its first value, NumPy scalars are shown as Python scalars) or `shown_argument` (a whole argument, arrays as lists), and tests check them with `pytest.raises(..., match=)`. The exception and warning types are public, the wording is not (`docs/api/compatibility.rst`).
- **Weights:** where a function takes `weights`, they are frequency weights: integer weights equal repeated rows, which the tests check. `docs/api/conventions.rst` lists the functions that take none. Weighted quantiles use the inverted CDF (`_edges.weighted_quantile`, implemented here because NumPy 1.24 has no `weights` in `np.quantile`), while unweighted quantiles interpolate linearly, so quantile edges agree with repeated rows only where no interpolation is involved and unit weights are not identical to no weights.
- **Scores summed column by column:** a score that a metric ranks, or a result that must be the same on every CPU, is summed column by column (as in `selection_path` and `most_prudent_pd`), not computed with a matrix product, because `X @ coef` can give identical rows different last digits and split ties. Internal fits such as `_logit.fit` may use matrix products.
- **Tables:** the index name, the column names and their order of every returned table are public (`docs/api/compatibility.rst` lists them all): a minor release only appends columns, and a PR that adds a table or a column updates that list.

### Counting semantics

All metric functions share `_counts.py`, which defines the counting and smoothing semantics. Change behavior there, not per metric:

- `group_counts` uses `pd.factorize(use_na_sentinel=False)`: missing values form their own group and unused categorical levels are dropped. Categorical groups are factorized with `sort=True` (category order, missing last); other groups with `sort=False` (first-observed order). The result index is named `bin`.
- Counting uses `np.bincount` on `2 * code + side`. With `weights` the counts are sums of weights (`_validation.as_weights` checks and aligns them like `target`), and groups whose weights sum to zero are dropped. `smoothing` is in units of weight; it is not rescaled.
- `shares` replaces zero cells with `smoothing` (default 0.5) and then normalizes each column independently. Count columns in the output stay raw; only the `*_share` columns reflect smoothing.
- `divergence(counts, smoothing)` takes an `(n, 2)` count array and returns the shares, `ln(b / a)` and `(b - a) ln(b / a)` per row. With (non-event, event) columns these are WOE and IV, and with (reference, current) columns the PSI terms. `woe_table`, `psi_table`, the count-based `woe` / `iv` / `psi` and the supervised binning helpers all go through it. The count functions check that two count Series have identical indices with `_validation.shared_index` and validate the counts with `_validation.as_count_columns`.
- Output columns: `woe_table` → `non_event, event, total, non_event_share, event_share, total_share, event_rate, woe, iv` (only the two class shares are smoothed; `total_share` and `event_rate` use raw counts); `psi_table` → `reference, current, reference_share, current_share, psi`. `woe_table` requires `groups` and `target` to have identical indices and both classes present.

### Typing

- Every function is annotated, and `src/kivi/py.typed` ships the hints. Use `npt.ArrayLike` for array_like inputs and `float | pd.Series | npt.NDArray[np.float64]` for results shaped by `like_input`; `_validation.DTypeObj` is the type of a NumPy or pandas dtype.
- A public function whose result type follows the type of an input keeps that union on its implementation and declares `@typing.overload` stubs in front of it (`...` bodies and defaults, no docstrings): `pd.Series` → `pd.Series` (one overload per argument that can make the result a Series), `float` → `float` where a scalar gives a float, `_validation.ListLike` (sequences, `pd.Categorical`, one-dimensional arrays) → an array or `pd.Categorical`, and last a catch-all that repeats the implementation's annotations. An overload declares only a type that the function returns for every argument of its types, and `tests/test_typing.py` checks each case with mypy and at run time.
- Use `_validation.is_real` / `is_integral` instead of `isinstance(x, Real)` / `isinstance(x, Integral)` on a value annotated `float` or `int`, because mypy does not know that `int` and `float` are registered as `numbers.Real` and would skip the rest of the function as unreachable.
- Every `# type: ignore` takes an error code and a reason. Do not subscript pandas classes (that raises at runtime on pandas 2.0) or use `from __future__ import annotations`.

## Versions and deprecations

- From 1.0 kivi follows semantic versioning, as `docs/api/compatibility.rst` promises: a deprecation warns with `FutureWarning` for the rest of the major version and takes effect in the next major release, and a fix of a wrong result may land in any release. `docs/release/migration.rst` lists what 1.0 removed.
- **Minimums:** Python 3.11 (from 1.9), NumPy 1.24 and pandas 2.0. A minimum rises only in a minor release that a `changed` fragment of the release before announces, together with `pyproject.toml`, the `minimum-versions` job and the versions on `install.rst` and `compatibility.rst` (`docs/development/releasing.rst`).
- **Deprecations** (there are none at present; the helper stays for later 1.x releases) warn through `_deprecation.warn`, which gives the warning to the first frame outside kivi, so it points at the caller's line however deep the check sits. `tests/test_deprecations.py` tests that, and each new deprecation adds its test there (`pytest.warns(FutureWarning, match=)` and the test's own file name) until the major release that removes it. Code and docs must never trigger a deprecation warning themselves, because pytest and the doctests treat warnings as errors.

## Bilingual documentation

- **Stack and layout:** Sphinx with pydata-sphinx-theme, numpydoc, sphinx-design (cards, tabs, buttons), sphinx-copybutton and MathJax. Pages are grouped by section folder (`getting_started/`, `tutorial/`, `user_guide/`, `release/`, `development/`) plus top-level `index.rst` and `api.rst`; the hidden toctree in `index.rst` defines the navbar (the Tutorial sits between Getting started and the User guide, hence `header_links_before_dropdown` 6).
- **Page lists:** `api.rst` and `user_guide/index.rst` end their toctrees with a glob (`api/*`, `*`), so a new page appears without editing them. Each glob must always match a page, or Sphinx warns and `-W` fails, so `api/datasets` and `datasets` are deliberately left out of the explicit lists. `user_guide/index.rst` lists the guides in the order of a project, and `api.rst` lists `api/conventions`, `api/compatibility`, `api/glossary` and the module pages in the same order; the integration PR moves a new guide and API page into those lists and updates the previous/next sentences of its neighbours. `validation` has no module page: it maps the ECB's validation report to functions of `calibration`, `metrics` and `vintage`.
- **API pages:** every API page starts with `.. module:: kivi.<module>`, a short introduction with links and a link back to its guide. `docs/api/conventions.rst` (the rules every function follows), `compatibility.rst` (what a release may change) and `glossary.rst` live under `api/` because `build.py` treats every user-guide page as an entry point. Feature PRs list the terms, rules and table columns they need for the integration PR.
- **The standard:** `docs/development/documentation.rst` defines the kinds of pages, the topic-guide outline and section titles, examples, charts and their color code, links (the first mention of a public name in each section is a `:func:` link), API pages, translations and entry points. `docs/build.py` fails when an API page lacks an `auto*` entry for a name in the module's `__all__` (read with `ast`), and lists the public functions missing from the README API tables and the guide pages without a README link or a card on `user_guide/index.rst`.
- **Tutorial and walkthrough:** `docs/tutorial/` is one credit scorecard project in eleven numbered chapters (`:numbered: 1`), from the applications to the IFRS 9 loss allowance; `user_guide/risk_workflow.rst` stays the short walkthrough on the bank data. The docs are positioned for credit risk and financial modeling, and the walkthrough is the end-to-end example: a `profile_table` screening, binning with a pointer to the constraints of `optimal_edges` and the optimistic development IV, WOE encoding, a saved `BinningSpec`, stepwise selection, scorecard, evaluation with the DeLong interval of the Gini, calibration on a master scale, a cut-off with its expected loss, and a PSI/CSI report that points on to monitoring, vintage and lifetime ECL. Each tutorial chapter starts with a collapsed `dropdown` that repeats the code it needs, so every page runs on its own. Results that only simulated data can give go in `.. admonition:: Simulation check` with `:class: kivi-check`, and no step depends on them. If a kivi change alters a printed tutorial table, regenerate it by running the page: the prose quotes many of its numbers.
- **Examples** are doctests with real output (`NORMALIZE_WHITESPACE` is on). If a change alters a printed DataFrame, regenerate the output by running the code rather than editing numbers by hand.
- **Charts:**
  - Charts are drawn at build time by matplotlib's `.. plot::` directive calling `figure_*` recipes in `docs/_plotting.py` (imported as `kp` via `plot_pre_code`). Each recipe recomputes the example shown in the doctest just above it, so change both together. The charts guide `user_guide/plotting.rst` instead calls `kivi.plotting` inline.
  - `plot_pre_code` also imports `_diagrams as kd` and `_tutorial as kt`. `kd.figure_*` recipes draw how a function computes its result with the numbers of the doctest above; a recipe that computes numbers itself checks them against the kivi function and raises otherwise. `kt.figure_*` rebuild the tutorial's project once and draw with the `_plotting` functions, so renaming a `_plotting` function means updating `docs/_tutorial.py` in the same PR.
  - In-chart text uses only kivi column and parameter names and data values, so one image serves both languages; captions and alt text are translated through the catalog. CJK text inside a chart would need CJK fonts on CI.
- **Translation:**
  - The Chinese edition comes from one gettext catalog, `docs/locale/zh_CN/LC_MESSAGES/kivi.po` (`gettext_compact = "kivi"`; `.mo` files are gitignored). Each msgid is the exact English string, **including public docstring paragraphs, table cells and math blocks**.
  - `docs/build.py` regenerates `kivi.pot` and fails on untranslated, fuzzy or stale entries, so after any English edit run `--update-po`, fill the empty/fuzzy `msgstr`s and remove the `#, fuzzy` flags. A markup-only change is applied to the msgid and the msgstr before `--update-po`, so the translations don't go fuzzy.
  - `--update-po` keeps the header's `POT-Creation-Date`, so pull requests only conflict where they change the same strings or neighbouring entries; resolve such conflicts with `--merge-po`, never by hand.
  - In translations keep a space (or CJK punctuation) around RST inline markup such as ``` ``code`` ``` and `` :doc:`x` ``, or docutils fails to parse it.
  - sphinx-design button labels are not extracted for translation; the home-page buttons therefore have no explicit text and show the target page's (translated) title.
- **Build output:** `docs/build.py` deletes and rebuilds `docs/_build/html`: `en/` and `zh/` are separate Sphinx builds (separate search indices), `docs/landing.html` is copied to the root as the language chooser, and `.nojekyll` is added for GitHub Pages. The language switch links to the same page name in the other edition, so both editions must keep identical page names. Brand colors, fonts and the home-page layout live in `docs/_static/kivi.css`; navbar extras are `_templates/version-badge.html` and `_templates/language-switch.html`.
- **Chinese search workaround:** `conf.py` replaces Sphinx's Chinese search language with a subclass because Sphinx 9.0 emits `window.Stemmer = ChineseStemmer` (undefined), which breaks search on the zh pages. Keep it until Sphinx fixes that.
- **CI:** `.github/workflows/docs.yml` has three jobs.
  - `build` runs ruff, mypy, `pytest --cov`, the doctests and `docs/build.py` on every pull request and every push to master. It is the required check: keep that job name and do not turn it into a matrix, or the required check never reports. On master it also force-pushes `docs/_build/html` to the `gh-pages` branch (served at https://gchensy.github.io/kivi/), replacing whatever was there.
  - `minimum-versions` runs pytest on Python 3.11 with NumPy 1.24.4 and pandas 2.0.3, the oldest versions `pyproject.toml` allows.
  - `newest-python` runs pytest on the newest Python release (3.15) with the newest NumPy, pandas and matplotlib. Move it to each new Python release when that comes out.
- **READMEs:** `README.md` (English, also the PyPI long description) and `README.zh-CN.md` (Chinese) mirror each other; keep them in sync. Because PyPI cannot resolve relative paths, every image and link in them is an absolute `raw.githubusercontent.com/.../master/` or `github.com/.../blob/master/` URL. The workflow diagrams are `docs/_static/kivi-workflow.svg` and `kivi-workflow.zh-CN.svg`, with dark-mode colors in an embedded `prefers-color-scheme` style. The quickstart output in both READMEs is pasted from a real run; regenerate it if the example or the data changes. The gallery images `docs/_static/readme-*.svg` are committed outputs of `python docs/_plotting.py` (deterministic thanks to `svg.hashsalt`); rerun it when a gallery recipe or its data changes.

## Releasing

- **Workflow:** `.github/workflows/release.yml` runs when a `v*` tag is pushed. The build job fails before anything is uploaded unless the tag is `v` plus the exact `version` in `pyproject.toml` and the tagged commit is on master; it also runs pytest and `twine check --strict` (which renders `README.md`). The publish job uploads to PyPI with trusted publishing through the `pypi` environment (no stored token), and only after that succeeds does a third job create the GitHub release with `gh release create --verify-tag --generate-notes` and the dist files attached (`a`/`b`/`rc`/`dev` versions become pre-releases). Do not create the GitHub release by hand first: the job would fail on the existing release.
- **Protection lives in repository settings, not in the code:** the `pypi` environment only accepts deployments from `v*` tags and has no required reviewers, so a pushed tag is uploaded without further approval; a tag ruleset ("Release tags") lets only admins create, move or delete `v*` tags; PyPI's trusted publisher is bound to `gchensy/kivi` + `release.yml` + environment `pypi`, so renaming the workflow file or environment breaks publishing until PyPI is updated.
- **Steps:** choose the version by `docs/development/releasing.rst` (a patch release only fixes; a minor release adds, deprecates or raises a minimum announced one release earlier; a major release removes what was deprecated). Bump `version`, run `python docs/build.py --release <version>` (it refuses while entry-point gaps remain; otherwise it writes the dated section from the fragments and deletes them) and translate the new heading, merge to master, then `git tag v<version>` on the merged commit and `git push origin v<version>`. The push publishes to PyPI; there is no approval step to stop it.

## Development workflow

Several Claude sessions often work on this repository at once. These rules keep their pull requests mergeable:

- **Scope first.** The session that splits up the work gives every parallel session a brief naming the files it owns. Two in-flight pull requests must not edit the same file; work that would is done one after the other, and a session that finds it needs a file another open PR changes says so instead of editing it. Usual hotspots: `src/kivi/binning.py`, `src/kivi/_counts.py`, `docs/conf.py`, `docs/user_guide/binning.rst`, `CLAUDE.md`.
- **A feature session only adds its own files**: `src/kivi/<module>.py`, `tests/test_<module>.py`, `docs/user_guide/<topic>.rst`, `docs/api/<module>.rst` and a release-note fragment. The globs pick up the new pages. `kivi.po` is the one shared file every PR may change; resolve its conflicts with `--merge-po`. Feature PRs must not add dependencies; a new runtime dependency or optional extra is the user's decision.
- **Shared entry points change only in an integration PR** that the coordinating session opens after a wave of feature PRs has merged: the README tables, gallery and roadmap (both languages), the title, steps and cards of `docs/index.rst`, the cards and order of `docs/user_guide/index.rst`, `docs/user_guide/risk_workflow.rst`, `docs/release/migration.rst`, the charts the feature PRs describe and this file. It rewrites them for the library as it now is instead of appending (see Entry points in `documentation.rst`). Keep this file to rules and the module map; a new function's algorithm belongs in its docstring and its release's design document.
- **Branch from the latest `origin/master`** (fetch first), one topic per pull request. Stack a pull request on an unmerged branch only when the work depends on it, and say so in its description.
- **Design documents** go in `docs/design/` as Markdown, with the user's decisions and the source checks of a release (`kivi-1.3-features.md` to `kivi-1.8-roadmap.md` and `kivi-1.8-default-rates.md`; releases before 1.3 and 1.9 have none). Sphinx reads only `.rst`, so they are not part of the built documentation and need no translation; the guides and the migration guide restate what users need.
- **Release notes go in fragments**: add `docs/release/unreleased/<topic>.<category>.rst` (category `new`, `changed`, `fixed` or `removed`) with one bullet item per user-facing change. Never edit the Unreleased section of `docs/release/index.rst`; the `release-fragments` directive in `docs/_fragments.py` renders the fragments there. A fragment is translated like any other text.
- **master is protected** by the repository ruleset "master": no direct or force pushes and no deletion; a change lands through a pull request whose `build` check passed on a branch that is up to date with master, so every PR is tested on top of everything merged before it. Merged branches are deleted automatically.
- **Merging is done on request.** A session merges only pull requests the user asked it to merge, in dependency order: bring the branch up to date by merging `origin/master` into it (not rebasing; PRs with Auto-fix must not be force-pushed), resolve a `kivi.po` conflict with `--merge-po`, wait for `build`, merge with `gh pr merge --merge`, then tell the sessions whose open PRs touch the same files to merge master.
- **Decisions that stay with the user**: priorities and scope, changes to the public API, merges that were not delegated, and releases (pushing a `v*` tag, which publishes to PyPI at once and cannot be undone).

## Scope and design constraints

From `docs/development/legacy_review.rst` and `docs/release/migration.rst`:

- **Dependencies:** at runtime the core depends only on NumPy and pandas. `kivi.plotting` needs matplotlib through the optional `plot` extra and imports it inside its functions, and scikit-learn, SciPy and statsmodels are references of the tests only (`test` extra). The user allowed scikit-learn as a dependency on 2026-11-22 and approved this split; a new runtime dependency or extra is the user's decision. Infrastructure-specific code (Spark, SQL, etc.) belongs in optional integrations and must not be imported at module load.
- **Out of scope.** Spark, SQL and model wrappers exist only in git history before commit 740ea6c. The user decided not to build the Spark and SQL integrations. `kivi.features` re-implements in pandas what the legacy Spark feature tools computed, without their Hive writers, cross features or industry percentile ranks (`docs/design/kivi-1.3-features.md`).
- **Re-implemented, not ported.** Every port of a legacy tool was checked against the legacy outputs or a reference implementation (statsmodels, SciPy, scikit-learn, mpmath, empulse, optbinning); `docs/release/migration.rst` lists how each one differs from its legacy counterpart. Records of the legacy checks: CSI against `evaluate/csi.py`; vintage tables against `VintagePd`; Best-KS against a re-run of `KSBins`, whose IV it matches or beats where `KSBins` does not crash; the AHP geometric weights against `ahp.py` to 1e-16, with its λ 7.4078 and CR 0.2271 on Saaty's school matrix reproduced by its estimate (the exact eigenvalue is 7.4199); `vif_filter` and `selection_path` against `VIF.LowVIFFeatures` and `StepWise` on the bank WOE data (largest p-values to 1.6e-12, AUCs to 2.7e-7; the drops differ where the legacy VIF without an intercept or its smallest-sum rule decide); `woe_trend` one to one with the legacy `monotony` labels on 20,000 random sequences without ties. When porting anything else, validate against fixed reference samples first.
- **`tests/test_reference.py` repeats the cross-checks against scikit-learn, SciPy and statsmodels in CI.**
  - Every test does `pytest.importorskip` for its library.
  - Selections chosen from the data are compared exactly, and computed floats with a `rel` tolerance and `abs=0`.
  - A failing cross-check is a possible wrong result: do not loosen it. Mark a documented difference of definition `xfail(strict=True)`.
  - Values of libraries that are no test dependency are hard-coded in the module's own test file instead (empulse in `test_metrics.py`, optbinning in `test_supervised_binning.py`). Feature PRs put their cross-checks behind `importorskip` in their own test file, and the integration PR moves them here.
  - The lower bounds of the `test` extra (scikit-learn 1.3, SciPy 1.12, statsmodels 0.14) were checked locally on Python 3.11 with NumPy 1.24.4 and pandas 2.0.3; CI installs newer releases.
  - Known precision limits of `_stats`: `betainc` at extreme arguments is about 1e-9 relative, and `gammaincc` reaches about 4e-10 relative at a = 1e5. `student_t_sf` stays within about 4e-13 of SciPy for t from 1e-8 to 40 and 1.5 to 1e9 degrees of freedom. `beta_quantile` solves SciPy's `betainc` to about 1e-12 relative for shapes up to 1e4 (1e-10 up to 1e6), and `bivariate_normal_cdf` keeps about 1e-14 relative for ρ ≥ 0 and probabilities above 1e-10.
- **Tests** assert raw counts, normalized shares and hand-calculated metric values (the legacy tests only printed tables); follow that pattern. Values from published tables (Basel II Annex 5, Pluto and Tasche, Tasche 2013) are hard-coded in the module's test file, with the tolerance and any cells that differ stated there.
